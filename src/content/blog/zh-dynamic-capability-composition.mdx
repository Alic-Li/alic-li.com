## 第一层：别重新造弓，先学会换箭 🏹

RWKV 这东西有一个我一直非常喜欢的特性：

<strong>State</strong>

Transformer 服务器天天围着 KV Cache 搓基础设施。  
RWKV 作为一个 recurrent model，本身就天然存在一个不断向前传递的 recurrent state。  
而且这个东西不是抽象概念。

Bo 官方的 RWKV-7 CUDA 实现里面就有非常直球的 `state passing` kernel：

forward 吃进去 `s0`，跑完一段 sequence 后吐出 `sT`；backward 还能从 `dsT` 一路往回产生 `ds0`。换句话说，<strong>State 本来就是整个 recurrent computation graph 里面可以显式输入、显式输出的一等对象。</strong>

[Bo 的 RWKV-CUDA state passing 实现](https://github.com/BlinkDL/RWKV-CUDA/tree/main/rwkv7_fast_fused/cuda)

这件事情很重要。  
因为它意味着：

<strong>我不一定要改模型参数，才能改变模型执行任务时的行为。</strong>

我可以先改：

> <strong>模型从什么状态进入这个任务。</strong>

所以我对 State Tuning 最直觉的理解一直不是：

> “一种更小的 LoRA。”

而是：

> <strong>Runtime-space adaptation。</strong>

模型还是那套 Weight。

但是：

```text
State A
   ↓
Same RWKV Weight
   ↓
Trajectory A
```

换一个：

```text
State B
   ↓
Same RWKV Weight
   ↓
Trajectory B
```

同一套动力系统。不同初始条件。最后模型进入的运行轨迹就不一样。  
所以我现在喜欢用一句话概括：

> <strong>State 决定模型“怎么进入这个任务”。</strong>

这时候 Minecraft 理论已经可以登场一半了：

<strong>
  <em>Bo 已经给你造好了一把弓。🏹</em>
</strong>

<strong>
  <em>State</em>
</strong>
是什么？

<strong>
  <em>箭。</em>
</strong>

今天：🏹 翻译箭  
明天：🏹 Tool Calling 箭  
后天：🏹 HTML 箭  
哪天闲得蛋疼：🏹 鹈鹕骑自行车箭🤣

弓还是那把弓。你只是换了箭。

## 感谢地表最强 PEFT 厨师长 JL 给我做了一桌菜 🍳

这哥们我现在已经不想叫他 PEFT Researcher 了。我愿称之为：地表最强 PEFT 厨师长 👨‍🍳  
各种 PEFT 菜系端上来一桌。LoRA / NoRA / DiSHA / MiSS 🤤

最后我吃了一圈：<strong>我发现我还是最喜欢 MiSS 这道菜。😋</strong>

MiSS 全称 <strong>Matrix Shard Sharing</strong>。论文的核心思路之一，是不用 LoRA 经典的 `A + B` 两个矩阵，而是利用 shard sharing 和一个共享可训练矩阵 `D` 来构造参数更新；其高效形式 MiSSᵉ 进一步把输入侧处理变成 blockwise aggregation。论文给出的核心对比非常直接：LoRA 是 `ΔWx = B(Ax)`，MiSSᵉ 则可以写成 `ΔWx = DS`，其中 `S` 是按块聚合后的输入。([arXiv](https://arxiv.org/abs/2409.15371))

[JL 的 MiSS GitHub](https://github.com/Joluck/MiSS) [MiSS 论文：arXiv:2409.15371](https://arxiv.org/abs/2409.15371)

传统 LoRA 大概是：

```text
x
│
├────────────── W₀x
│
└── A ── B ─── Δx
```

MiSSᵉ 更像：

```text
x
│
├────────────── W₀x
│
└── block sum ─ D ─ Δx
```

而论文里对这种 single-matrix paradigm 的分析也很漂亮：在其给出的复杂度模型中，LoRA 参数量为 `O(r(k+d))`，MiSSᵉ 则是 `O(rd)`；输入变换阶段也从 `Ax` 的矩阵乘变成 block sum。([arXiv](https://arxiv.org/html/2409.15371v12))

这就非常对我的胃口了。因为我这个人做东西有一个很朴素的审美  
（不是因为懒也不是因为东西加太多容易Buggy，（逃

> <strong>能少一个 Matrix 就少一个。</strong>
> <strong>能少一次 GEMM 就少一次。</strong>
> <strong>能少搬一点显存就少搬一点。</strong>
> 毕竟最后还不是得多写 Kernel多烧Token 😭

所以我最后把 MiSS 塞进了自己的 `rwkv_lightning_cuda`。

现在我的实现是每个目标 Linear 训练一个紧凑的 `D`，Base Weight 保持冻结；训完以后 Adapter 可以在请求级动态加载，而共享 Base Model 不需要被原地改掉。([GitHub](https://github.com/Alic-Li/rwkv_lightning_cuda))

然后事情就开始变得好玩了😇

## State 是换箭，MiSS 是给弓渗透性附魔 🏹✨🔮

这里就是整篇想法真正的核心。  
我越来越不愿意把 State Tuning 和 MiSS 当成：

> 两种互相竞争的 PEFT。

因为它们根本没在改同一个东西。  
我现在对它们的理解是：

> <strong>State 决定模型“怎么进入这个任务”。</strong>
> <strong>Adapter 决定模型“在每一层怎么处理这个任务”。</strong>

换成稍微正经一点的术语：<strong><em>Runtime-space adaptation + Weight-space adaptation</em></strong>

<strong>State</strong>：

```text
改变 recurrent dynamics 的起点 / 轨迹
```

<strong>MiSS</strong>：

```text
改变每一层局部 Weight Mapping
```

也就是说：

```text
Same Base Model
                       │
        ┌──────────────┴──────────────┐
        │                             │
Runtime-space                    Weight-space
        │                             │
      State                     MiSS Adapter
        │                             │
   改运行轨迹                     改局部映射
```

它们不是完全重叠的自由度。所以叠起来的时候，就有机会比只用其中一边更有表达力。

这也是我为什么越来越喜欢 Minecraft 弓箭附魔理论。🤣

## 真正有意思的不是 MiSS，而是推理的时候组合它

做到这里以后，我突然发现：  
MiSS 本身反而不是最有意思的部分。

真正让我觉得开始邪门的是：

<strong>为什么 Adapter 一定要在启动模型的时候固定？</strong>

为什么不能：

```text
Request A
→ State A
→ Adapter A
→ Shared Base
```

下一个请求：

```text
Request B
→ State B
→ Adapter B
→ Same Shared Base
```

再下一个：

```text
Request C
→ State C
→ Adapter C
→ Still Same Base
```

于是就有了我现在这套：

## Dynamic State Loading + Dynamic MiSS Adapter Loading

在 `rwkv_lightning_cuda` 里面，上传后的 State 可以通过 `state_id` 直接绑定到生成请求；MiSS Adapter 则可以通过 `adapter_id`、`adapter_version`、`adapter_scale` 在 request admission 时选择。Adapter 注册时先留在 CPU RAM，第一次真正使用时才整包上传 GPU，prefill 和 decode 会继续复用，而不是每层、每 token 来回搬。([GitHub](https://github.com/Alic-Li/rwkv_lightning_cuda/blob/main/docs/http-api.md))  
甚至我还专门处理了最容易翻车的地方：

<strong>State 不能串味。</strong>

Stateful session 的 identity 里面现在会考虑 Base Model lifetime、Adapter content version、scale、initial state 和 WKV precision；组合对不上，就不能拿一个旧 State 硬续。([GitHub](https://github.com/Alic-Li/rwkv_lightning_cuda/blob/main/docs/http-api.md))  
不然今天：

```text
HTML State + SVG Adapter
```

跑着跑着第二天：

```text
Tool State + Function Adapter
```

结果 Runtime：

> “来来来，这里还有昨天剩下半碗鹈鹕汤，我给你热一下。”

那就真的完蛋了。🤣

## 所以我现在更愿意把它叫 Capability Composition

以前我的脑子里面是：

```text
Model = weights.pth
```

现在越来越像：

```text
Model Behavior = Base + State + Adapter + Request Context
```

重点不是：

> “我今天加载哪个模型？”

而是：

> <strong>“我今天怎么组合这个模型？”</strong>

这个变化我觉得挺大的。因为这样的话：  
一个 7.2B Base 并不一定只能代表“一只模型”。  
它可以更像：<strong>一个共享的计算底座。</strong>

上面挂：

```text
State A State B State C ...
MiSS A MiSS B MiSS C ...
```

然后 Runtime 根据请求现场组装。

这就是我说的：<strong>Dynamic Capability Composition</strong>  
能力不再必须是一整块巨大的 <strong>Weight Blob。</strong>  
能力可以开始变成：<strong>Composable Objects。</strong>

## Adapter 也应该是 Runtime Asset

同样的道理。我不想：

```text
启动 Server ---> 加载 Adapter A ---> 重启 ---> 加载 Adapter B ---> 重启---> 加载 Adapter C
```

这也太 2023 了，我要2077 🤣  
我更希望：

```text
Adapter Registry
├── html
├── tool
├── translate
├── medical
└── pelican_bicycle
```

Request 来了：

```text
{
  "model": "rwkv-7.2b",
  "state": "html-vibe",
  "adapter": "pelican-svg"
}
```

Runtime：

> “哦，今天要骑车是吧。”

啪。挂上。下一个：

```text
{
  "model": "rwkv-7.2b",
  "state": "tool-call",
  "adapter": "function-call"
}
```

Runtime：

> “行，鹈鹕下班。”

🤣

我的实现现在 Adapter 第一次 request 才触发 GPU upload，后续 prefill / decode 复用 GPU resident adapter，并且有 RAM/GPU cache hit、miss、upload、H2D 时间等指标可以看。([GitHub](https://github.com/Alic-Li/rwkv_lightning_cuda/blob/main/src/miss/README.md))  
这才是我想要的 PEFT serving。

<strong>不是训完一个小文件，然后高兴地把它丢在硬盘里面。</strong>
而是真的把：

> <strong>PEFT 变成 Runtime 原语。</strong>

## 这次为什么 36MB 给我的震撼这么大

其实不是因为：

> “哇，36MB 好小。”

单纯文件小并不稀奇。PEFT 本来就是干这个的。真正让我觉得邪门的是：

<strong>能力密度。</strong>
在足够针对性的数据里面，一个很小的局部 Weight
Update，可以明显改变模型在某一类任务上的行为。 所以那个鹈鹕 Demo
真正让我在意的不是鸟。 而是：

> <strong>
>   局部低成本参数更新，对专一技能的注入效率，可能比我们的直觉高得多。
> </strong>

如果这个判断成立，那么一个很自然的工程方向就是：  
不要：

```text
Task A → Model A
Task B → Model B
Task C → Model C
```

而是：

```text
State A + Adapter A
            /
Shared Base ─ State B + Adapter B
            \
             State C + Adapter C
```

<em>
  <strong>
    一个 Base。一堆很便宜的小能力模块。Runtime 帮你组合。这就开始有点意思了。
  </strong>
</em>

## 当然，36MB 里面也没有霍格沃茨 🪄

我不觉得小 Adapter 是什么万能灵药。  
它不可能：

> Base 完全不会微积分，你拿 10MB Adapter 就让它突然证明黎曼猜想。🤣

Adapter 和 State 能注入、强化、重组织能力，但它们仍然建立在 Base Model 原有表示能力之上。

而且：

<strong>数据质量仍然非常重要。“Trash in trash out”</strong>
如果你的训练集里面全是垃圾：MiSS 也不能把垃圾炼成仙丹。

最多：

<strong>高参数效率地炼出浓缩垃圾。😭</strong>

还有一个更重要的问题：State 和 Adapter 的自由度到底有多互补？  
在什么任务上：

```text
State only
```

已经够了？什么时候：

```text
MiSS only
```

更适合？什么时候：

```text
State + MiSS
```

会明显更强？  
这个得靠 ablation 来说话。我接下来也比较想系统跑：

```text
Base
State only
MiSS only
State + MiSS
```

而不是只放一只鹈鹕然后宣布：

> <strong>AGI 已解决。</strong>🤣

## 最后：我越来越不把“模型”看成一份 Weight 了

以前：

```text
Model = model.pth
```

现在：

```text
Base Weight
                  │
          ┌───────┴───────┐
          │               │
       State           Adapter
          │               │
   Runtime Space      Weight Space
          │               │
          └───────┬───────┘
                  │
               Request
                  │
                  ▼
          Current Behavior
```

所以我现在越来越愿意把模型理解成：

<strong>一个 Runtime。</strong>
<strong>
  <em>
    Base Weight 只是底座。State 是可编程的运行状态。Adapter 是可插拔的局部
    Weight Modification。
  </em>
</strong>
Prompt 还是 Prompt。Sampling 还是 Sampling。 最终它们共同组成：
<strong>这个请求此刻真正运行的“模型”。</strong>
