Recently, I've been doing something increasingly ridiculous.  
I took **RWKV-7.2B**, attached a MiSS Adapter of only a few dozen MB, and fed it some HTML / SVG data I had put together.  
And this is what it produced: **a pelican riding a bicycle.**

> I stared at the screen for quite a while. **I started wondering whether I'd downloaded a bootleg RWKV.** Was I running the wrong model? **An adapter of around 36 MB had stuffed a whole pelican in there. 🤣**

And let me emphasize: **this is only 7.2B.**

But the pelican experiment was **never an SVG benchmark**. It was a deliberate overfit stress test. I constructed a small dataset that would be easy to overfit, first to check that the entire training → saving → loading → dynamic attachment → inference infrastructure was correct, and also to see how much complex, long-form structure such a small State / Adapter could actually memorize.

My original expectations were fairly pessimistic: with HTML / SVG running to thousands of tokens, the model would probably start repeating itself, break tags, lose the structure, or simply drift during generation.

**What surprised me most wasn't that it could draw a pelican. It was that a local parameter update of just a few dozen MB could reliably encode and reproduce such long, structurally fragile output. 🤣**

As for genuine generalization, that's a question for the next set of experiments. I've also tried combinations outside the training examples, such as “Qin Shi Huang riding a polar bear.” The model could still generate relevant code, so it wasn't merely repeating the training text verbatim. The resulting SVG did get rather abstract 🤣, but it didn't loop, and the HTML still closed properly and rendered. Honestly, that alone made me pretty happy, haha.  
More precisely, **it showed some transfer and compositional ability, but I had clearly overfit this MiSS pretty hard. A serious run with more data should work very well.** 😋

The next thing genuinely worth testing is: **after attaching this State / Adapter, does the model's ability to do other things deteriorate, stay roughly unchanged, or actually improve?**  
I couldn't be bothered to bring out the 13.3B model this time. Partly laziness, partly because its capabilities are already a bit overpowered. _Mostly, though, I don't have much compute, and writing the NCCL operators for my infrastructure has been giving me a headache. I'll stick to single-GPU training for now. (Runs away.)_

What I really want to know is: **how far can a reasonably sized base model go with a very small local parameter update?**  
Judging by the results so far… things are getting suspicious. 🤣

### I started wondering: why do we build a whole new model every time we add an ability?

There's a very natural mindset in today's LLM ecosystem: the model isn't strong enough? **Scale up.** Not capable enough? Get a bigger one. Of course, I'm not saying scaling doesn't work. Brute force does get things done. Big models must be big ✋😭✋. Bigger is better 😭.  
Then: poor results in a particular domain? Fine-tune a new model. Another business use case? Fine-tune another one. 🥲  
Eventually your server's disk looks like this:

```text
model_final.pth
model_final_v2.pth
model_final_v2_fixed.pth
model_final_really_final.pth
model_final_this_time_really_final.pth
```

The classic experiment-directory junkyard. 🤣 (My disks do, in fact, look like this. 😇)

A model's foundational capabilities, knowledge capacity, and reasoning ceiling certainly depend on the base model. RWKV has kept iterating on its pretraining data, and its base models have steadily improved. These days, running fast doesn't seem to earn you much, which is a little depressing. But the ones that keep running, even slowly, just refuse to die.

But I increasingly feel that **not every capability upgrade is worth modifying the entire model. Many skills only need a perturbation of a few dozen MB—local in size, yet affecting parameters across the model.**

If your faucet leaks, your first reaction shouldn't be: **blow up the building and rebuild it.** 🔨🤣

So here's the question: **can we treat the model itself as a stable computational base, separate out individual capabilities, and compose them dynamically at runtime?**  
In other words:

```text
Stable Base Model
      +
Runtime State
      +
Weight Adapter
      =
The model behavior actually used by this request
```

That's what I've been working on in `rwkv_lightning_cuda`. This isn't just another PEFT implementation.

It's:

## Dynamic State Loading + Dynamic MiSS Adapter Loading

Or, to give it a flashier name:

## Dynamic Capability Composition

Composing capabilities dynamically.

## Layer one: don't rebuild the bow—learn to swap arrows first. 🏹

RWKV has a feature I've always particularly liked:

<strong>State</strong>

Transformer servers spend their days building infrastructure around the KV cache. As a recurrent model, RWKV naturally has a recurrent state that passes forward through the computation. And this isn't just an abstract concept.

Bo's official RWKV-7 CUDA implementation has a very explicit state-passing kernel:

The forward pass takes `s0` and returns `sT` after processing a sequence; backward can propagate from `dsT` all the way back to `ds0`. In other words, **State is already a first-class object that can be explicitly passed into and out of the recurrent computation graph.**

[Bo's RWKV-CUDA state-passing implementation](https://github.com/BlinkDL/RWKV-CUDA/tree/main/rwkv7_fast_fused/cuda)

This matters, because it means:

I don't necessarily have to change the model's parameters to change how it behaves on a task.

I can first change:

> The state from which the model enters the task.

So my most intuitive understanding of State Tuning has never been:

> “A smaller kind of LoRA.”

Instead, it's:

> Runtime-space adaptation.

The model still uses the same weights.

But:

```text
State A
   ↓
Same RWKV Weight
   ↓
Trajectory A
```

Swap the state:

```text
State B
   ↓
Same RWKV Weight
   ↓
Trajectory B
```

The same dynamical system. Different initial conditions. The model ends up following a different trajectory. So I now like to summarize it this way:

> State determines “how the model enters the task.”

At this point, half of my Minecraft theory can already make its entrance:

Bo has built you a bow. 🏹

What is State?

The arrow.

Today: 🏹 a translation arrow.  
Tomorrow: 🏹 a tool-calling arrow.  
The day after: 🏹 an HTML arrow.  
And when you're bored out of your mind: 🏹 a pelican-riding-a-bicycle arrow. 🤣

It's still the same bow. You're just changing the arrow.

## But then I realized: swapping arrows isn't enough

State is great: cheap, small, and, as a recurrent state, naturally easy to move around at runtime. But the limitation is obvious too. Some abilities can't be fully addressed just by changing where the model starts. Sometimes I really do want to touch **the local mapping inside the linear layer itself**. That's when it's time to enchant the bow. 🤣 In other words: **an adapter**.

## Thanks to JL, the world's finest PEFT chef, for serving me a whole feast. 🍳

I don't even want to call this guy a PEFT researcher anymore. I hereby declare him **the world's finest PEFT chef**. 👨‍🍳 A whole table of PEFT dishes: LoRA / NoRA / DiSHA / MiSS. 🤤

After trying them all, I found that **MiSS was still my favorite dish**. 😋

MiSS stands for **Matrix Shard Sharing**. One of the paper's central ideas is to construct parameter updates through shard sharing and a shared trainable matrix `D`, rather than LoRA's classic pair of matrices, `A + B`. Its efficient form, MiSSᵉ, further replaces input-side processing with blockwise aggregation. The paper's core comparison is direct: LoRA computes `ΔWx = B(Ax)`, while MiSSᵉ can be written as `ΔWx = DS`, where `S` is the block-aggregated input. ([arXiv](https://arxiv.org/abs/2409.15371))

[JL's MiSS GitHub](https://github.com/Joluck/MiSS) · [MiSS paper: arXiv:2409.15371](https://arxiv.org/abs/2409.15371)

Traditional LoRA looks roughly like this:

```text
x
│
├────────────── W₀x
│
└── A ── B ─── Δx
```

MiSSᵉ is more like:

```text
x
│
├────────────── W₀x
│
└── block sum ─ D ─ Δx
```

The paper's analysis of this single-matrix paradigm is also elegant. In its complexity model, LoRA has `O(r(k+d))` parameters, while MiSSᵉ has `O(rd)`. The input transformation also changes from the matrix multiplication `Ax` to a block sum. ([arXiv](https://arxiv.org/abs/2409.15371))

This is exactly my kind of thing. My engineering taste is very simple. (Not because I'm lazy, or because adding too much stuff makes things buggy. Runs away.)

> One fewer matrix whenever possible. One fewer GEMM whenever possible. A little less VRAM traffic whenever possible. Otherwise, I just end up writing more kernels and burning more tokens anyway. 😭

So I ended up putting MiSS into my own `rwkv_lightning_cuda`.

My implementation trains a compact `D` for each target linear layer while keeping the base weights frozen. Once trained, the adapter can be loaded dynamically per request, without modifying the shared base model in place. ([GitHub](https://github.com/Alic-Li/rwkv_lightning_cuda))

Then things started getting fun. 😇

## State swaps the arrow; MiSS enchants the bow from within. 🏹✨🔮

This is the real core of the whole idea. I'm increasingly reluctant to treat State Tuning and MiSS as:

> Two competing forms of PEFT.

Because they're not changing the same thing at all. Here's how I understand them now:

> State determines “how the model enters the task.” An adapter determines “how the model processes the task at each layer.”

In slightly more formal terms: **runtime-space adaptation + weight-space adaptation**.

State:

```text
Changes the starting point / trajectory of recurrent dynamics
```

MiSS:

```text
Changes the local weight mapping at each layer
```

In other words:

```text
Same Base Model
                         │
          ┌──────────────┴──────────────┐
          │                             │
   Runtime-space                  Weight-space
          │                             │
        State                     MiSS Adapter
          │                             │
  Changes trajectory             Changes local mappings
```

These aren't completely overlapping degrees of freedom. Combining them therefore has the potential to be more expressive than either one alone.

That's also why I'm increasingly fond of my Minecraft bow-and-enchantment theory. 🤣

## The interesting part isn't MiSS itself—it's composing it at inference time

Once I got this far, I realized that MiSS itself wasn't actually the most interesting part. What really started to feel wild was this: **why must an adapter be fixed when the model starts?**

Why can't we do this:

```text
Request A
→ State A
→ Adapter A
→ Shared Base
```

Then the next request:

```text
Request B
→ State B
→ Adapter B
→ Same Shared Base
```

And the one after that:

```text
Request C
→ State C
→ Adapter C
→ Still Same Base
```

That leads to my current setup:

## Dynamic State Loading + Dynamic MiSS Adapter Loading

In `rwkv_lightning_cuda`, an uploaded State can be attached directly to a generation request through `state_id`. A MiSS Adapter can be selected at request admission with `adapter_id`, `adapter_version`, and `adapter_scale`. Registered adapters initially remain in CPU RAM. The complete adapter is uploaded to the GPU only on first use and then reused throughout prefill and decode, rather than being moved around at every layer or token. ([GitHub](https://github.com/Alic-Li/rwkv_lightning_cuda/blob/main/docs/http-api.md))  
I even specifically handled one of the easiest things to get wrong:

**States must not get mixed up.**

A stateful session's identity now takes into account the base model's lifetime, adapter content version, scale, initial state, and WKV precision. If the combination doesn't match, an old State cannot simply be continued. ([GitHub](https://github.com/Alic-Li/rwkv_lightning_cuda/blob/main/docs/http-api.md)) Otherwise, today you have:

```text
HTML State + SVG Adapter
```

And tomorrow, midway through a run:

```text
Tool State + Function Adapter
```

Then the runtime says:

> “Come on over. I've still got half a bowl of yesterday's pelican soup. Let me warm that up for you.”

And then you're truly done for. 🤣

## So I now prefer to call it Capability Composition

I used to think:

```text
Model = weights.pth
```

Now it's increasingly like:

```text
Model Behavior = Base + State + Adapter + Request Context
```

The key question isn't:

> “Which model am I loading today?”

It's:

> “How am I composing this model today?”

I think this is a significant shift. A 7.2B base doesn't necessarily have to represent just one model. It can instead be **a shared computational foundation**.

On top of it, attach:

```text
State A State B State C ...
MiSS A MiSS B MiSS C ...
```

Then the runtime assembles the combination for each request.

That's what I mean by **Dynamic Capability Composition**. A capability no longer has to be one enormous weight blob. Capabilities can start becoming **composable objects**.

## Why 36 MB made such a big impression on me this time

It wasn't just:

> “Wow, 36 MB is so small.”

A small file alone isn't remarkable. That's what PEFT is for. What really struck me was **capability density**. With sufficiently targeted data, a small local weight update can visibly change a model's behavior on a particular class of tasks. So what interested me about the pelican demo wasn't the bird. It was this:

> Low-cost local parameter updates may inject specialized skills far more efficiently than our intuition suggests.

If that holds, a natural engineering direction is to move away from:

```text
Task A → Model A
Task B → Model B
Task C → Model C
```

And toward:

```text
State A + Adapter A
            /
Shared Base ─ State B + Adapter B
            \
             State C + Adapter C
```

One base. A collection of inexpensive little capability modules. A runtime to compose them. Now that's getting interesting.

---

## Of course, there isn't a Hogwarts hidden inside those 36 MB. 🪄

I don't think a small adapter is some miracle cure. It can't do this:

> “The base model doesn't understand calculus, but a 10 MB adapter suddenly makes it prove the Riemann hypothesis.” 🤣

Adapters and States can inject, strengthen, and reorganize abilities, but they still depend on the base model's existing representational capacity.

And **data quality still matters enormously**. “Trash in, trash out.” If your training set is garbage, MiSS can't turn it into an elixir.

At best, it can produce concentrated garbage with high parameter efficiency. 😭

There's also a more important question: how complementary are the degrees of freedom in State and adapters? For which tasks is:

```text
State only
```

Already enough? When is:

```text
MiSS only
```

A better fit? And when is:

```text
State + MiSS
```

Clearly stronger? That needs ablations, not guesses. Next, I'd like to systematically run:

```text
Base
State only
MiSS only
State + MiSS
```

Rather than show one pelican and announce:

> “AGI solved.” 🤣

Before:

```text

```

```text
Base Weight
                  │
```
